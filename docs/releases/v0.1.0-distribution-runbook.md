# Kairoseth Fiscal / Puente VeriFactu v0.1.0 — distribución controlada

## Propósito

Runbook operativo para instalar, validar, actualizar y soportar la release técnica v0.1.0 sin activar AEAT producción.

La fuente funcional validada sigue siendo el candidato exacto `fe4c6360a2b25d44f5044e202f7d2bc2faa626a7`.

## Límite fiscal obligatorio

Esta release está **validada contra AEAT TEST** y mantiene **AEAT producción deshabilitada**.

Distribuir, instalar o etiquetar v0.1.0 no autoriza:

- `PV_AEAT_ENVIRONMENT=production`;
- `PV_AEAT_ALLOW_PRODUCTION=YES`;
- remisiones fiscales reales en producción sin gate separado y autorización explícita.

## Selección de canal

1. WooCommerce/WordPress: plugin oficial.
2. PrestaShop: módulo oficial.
3. ERP/CRM/SaaS/software propio con backend: API HTTP/JSON, webhook o adapter.
4. Excel/CSV/XLSX: onboarding cero-código con preflight.
5. Software local/legacy: Local Agent en modo read-only hacia el origen cuando corresponda.
6. Si no existe integración nativa: fallback universal por fichero/importación manual.

## Onboarding mínimo obligatorio

Toda instalación controlada debe completar este orden:

1. identificar organización, instalación y sistema origen;
2. seleccionar canal por capacidades, no por marca;
3. crear o reutilizar el Integration Profile correspondiente;
4. configurar mapping y credenciales solo donde apliquen;
5. ejecutar `preflight` sin efectos;
6. corregir errores o warnings antes de emitir;
7. confirmar explícitamente la activación del canal;
8. verificar estado operativo y ausencia de duplicados/reconciliaciones pendientes.

Los canales manuales no requieren bearer credential cuando `credentialApplicable=false`.

## WooCommerce

### Instalación

- Instalar únicamente el ZIP reproducido `0.3.0`.
- Verificar checksum antes de subirlo.
- Activar el plugin y revisar configuración del endpoint/token del puente.
- Mantener certificado, PFX, passphrase y reglas AEAT fuera de WordPress.

### Smoke mínimo

- plugin activable;
- compatibilidad HPOS;
- preflight de pedido sin efectos fiscales;
- issue idempotente en entorno permitido;
- persistencia de `recordId`/estado;
- refund/rectificativa sin duplicar reglas fiscales en WooCommerce.

### Fallback

Si una actualización de WordPress/WooCommerce bloquea el conector, desactivar automatización/emisión desde el plugin y utilizar la vía universal CSV/XLSX mientras se diagnostica.

## PrestaShop

### Instalación

- Instalar únicamente el ZIP reproducido `0.5.0`.
- Verificar checksum antes de cargar el módulo.
- Mantener los switches automáticos desactivados hasta completar preflight y validación.
- Las reglas fiscales sensibles permanecen server-side.

### Smoke mínimo

- módulo instalable y activable;
- lectura de factura nativa;
- construcción de payload neutral;
- preflight;
- persistencia del estado principal y rectificativo;
- upgrade preservando estado local;
- automatización OFF sin efectos laterales.

### Fallback

Desactivar automatización del módulo y usar exportación/importación universal hasta resolver la incidencia.

## Local Agent

### Requisitos

- Node.js 22 compatible con el bundle;
- instalación desde el ZIP cuyo SHA-256 coincide con la evidencia;
- conectividad saliente hacia Kairoseth Fiscal;
- acceso al sistema origen con permisos mínimos y preferentemente read-only.

### Smoke mínimo

- `status`/`doctor` correctos;
- lectura read-only del origen;
- servicio inicia y detiene correctamente;
- upgrade preserva estado compatible;
- rollback de código no restaura automáticamente la base de datos;
- no se escriben secretos ni payloads fiscales en logs públicos.

## API / starter kits

Los clientes Node, Python, PHP y curl usan el lifecycle:

`preflight -> issue -> status -> rectify/cancel`

El sistema cliente no debe asumir autoridad sobre `taxCode`, `regimeKey`, `operationClass`, `TipoHuella`, certificado ni transporte AEAT.

## Rollback

Política oficial: `code-first-no-automatic-db-restore`.

Ante una regresión:

1. detener nuevas emisiones del canal afectado;
2. conservar datos y estado durable;
3. volver al artefacto/código anterior conocido;
4. no restaurar MongoDB/SQLite automáticamente;
5. inspeccionar outbox y estados `pending`, `processing`, `reconciliation_required` y `blocked`;
6. reconciliar antes de cualquier reemisión cuando exista incertidumbre;
7. restaurar datos solo mediante procedimiento explícito y evidencia de backup/restore.

Nunca usar rollback como mecanismo para repetir una factura.

## Soporte y triage

Clasificación mínima:

- **Verde**: sincronizado/completed, sin acción.
- **Ámbar**: pendiente, retryable o en espera; no duplicar.
- **Rojo**: rejected, blocked o reconciliation_required; requiere diagnóstico.

En una incidencia registrar solo información sanitizada:

- versión del artefacto;
- canal;
- correlation/record id cuando sea seguro;
- código de error normalizado;
- estado del outbox;
- timestamps;
- resultado de preflight.

No incluir en tickets públicos PFX, passphrase, NIF, XML/SOAP crudo, credenciales MongoDB, tokens ni payloads fiscales completos.

## Criterio de distribución controlada

Una instalación se considera apta cuando:

- checksum coincide;
- preflight pasa;
- smoke específico del canal pasa;
- no hay duplicados;
- no hay reconciliaciones o bloqueos sin resolver;
- AEAT environment sigue en `test` durante esta fase;
- existe fallback documentado.
